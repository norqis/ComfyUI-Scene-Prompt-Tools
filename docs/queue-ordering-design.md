# Queue ordering and Count composition design

Status: design only; no runtime behavior is changed by this document.

## Version decision

Target package release: `v0.7.0`, provided saved workflows and documented output remain compatible. The internal `SCENE_PROMPT` plan schema changes from v6 to v7. A schema revision is not by itself a public major release. If implementation needs to change the output of an existing workflow, stop and revisit the public version and migration rather than silently shipping it. The mode defaults to the current input order. No installed ComfyUI copy should be changed while it is generating.

## User-visible contract

Scene Prompt Queue gains `並び順: 入力順 | 1件ずつ交互`. Existing workflows and absent API values mean `入力順`. `1件` means one Expand execution batch, not one image in a latent batch. An alternating Queue reads one batch from each connected input, in numbered socket order; exhausted inputs are skipped. A Queue with no connected inputs returns the same single seed `run` in **either** mode, with Queue-boundary provenance set; it does not construct an empty `alternate`. Count 0 yields no executions.

A Queue input whose effective plan already contains a Queue boundary locks the receiving Queue to `入力順`. This includes Reroutes, Scene transforms, and Preset References, not just a visually adjacent Queue. Its widget reads `入力順（上流Queueあり）` and is disabled. Connecting such an input normalizes a previously saved `交互` choice to `入力順`; disconnecting it does not resurrect that old choice. Graph load and connection changes refresh the widget. The Python node independently uses `入力順` when an input plan contains a Queue boundary, including direct API calls without the UI. A bypassed Queue leaves a boundary only if the effective bypass path actually contains one. Queue provenance is plan metadata; inspecting the whole graph at each execution or draw is unnecessary.

The backend declares `order_mode` as an **optional** combo input, with default `入力順`, so old API prompts pass ComfyUI's input validation before the Python default is used. `queue(order_mode="入力順", **scene_prompts)` and `IS_CHANGED` include the normalized effective mode and input fingerprints; invalid values are rejected with a clear error. The UI appends the new persistent value after the old Queue's stored values (the old Queue has no persistent mode widget); its non-serialized preview widget is never mistaken for that value. Workflow serialization, prompt/API serialization, connection changes, and `afterConfigureGraph` load normalization all use the same effective-mode rule. A locked Queue writes `入力順` to the saved widget and uses that value in the submitted prompt, while Python also enforces it for headless API callers. Preset serialization preserves the optional input. When Preset metadata is still loading, the UI treats the mode as temporarily unavailable rather than enabling a choice it cannot validate; it refreshes from a cached Queue-boundary summary when loading finishes.

For the target graph:

```text
A -> b1 --\
          Queue A [1件ずつ交互] --\
A -> b2 --/                         \
                                     Queue C [入力順, locked] -> Count D [10] -> Expand
A -> b3 --\                         /
          Queue B [入力順] --------/
A -> b4 --/
```

The resulting order is `(A-b1, A-b2) × 10`, then `A-b3 × 10`, then `A-b4 × 10`. Queue A's own mode remains active. Queue C does not specify separate modes for its children. If Queue A's inputs have unequal lengths, one complete alternating cycle drains both inputs; Count after Queue A repeats that complete cycle. For example, `b1 × 2` and `b2 × 3` make a cycle `b1,b2,b1,b2,b2`, and Count 2 makes that exact five-batch cycle twice. Count before Queue A instead changes each input stream before interleaving; these two placements intentionally differ.

Count repeats each **top-level output unit** of its incoming plan. A run of one row is a unit; an alternating Queue is one unit. An input-order Queue concatenates its children's top-level units and does not turn the entire concatenation into a new unit. Thus Count after an ordinary Queue remains exactly the current per-row Count for old workflows, while Count after an alternating Queue repeats the alternating sequence. Queue B's ordinary rows remain separate units when Queue C concatenates them. Count factors in series multiply, and Count 1 preserves structure.

## Plan representation and indexing

Plan v6 stores a flat list of `(row, contiguous count, start_index)`. Flattening an alternating Queue into that list destroys its grouping before downstream Count; materializing every batch would also use memory proportional to generation count. Plan v7 has one authoritative immutable schedule. The exact plan keys are `type`, `version`, `units`, `sources`, `contains_queue_boundary`, `stats`, and `change_key`. `sources` keeps the current Queue input summaries. `contains_queue_boundary` is a boolean set by **every** executed Queue, including an input-order Queue with zero events; transforms, Count, Matrix, Merge, and Preset markers propagate it by OR, while a bypass contributes only its effective source plan and a mute contributes none. It does not depend on leaf rows existing. Queue output sets it to true. UI lineage caches also carry this bit, so a changed empty Queue invalidates the lock state.

Each unit has a `kind` and `stats`; `stats` has exactly `total_batches`, `total_images`, `unset_batches`, and `row_count`. `unset_batches` counts events without a latent setting; their image batch size is one. Unit exact keys, in addition to `kind,stats`, are:

| Kind | Additional exact keys | Meaning |
| --- | --- | --- |
| `run` | `row,count` | One contiguous row run; zero count remains as a logical row for old metadata. |
| `alternate` | `inputs` | One atomic round-robin unit; each input is an ordered v7 plan in socket order. |
| `repeat` | `unit,factor` | Repeat the complete child unit; Count wraps each top-level unit, not every leaf. |
| `matrix_map` | `unit,matrix_rows` | For each event of an atomic child, emit its Matrix variants in Matrix row order. |
| `product` | `left,right` | Lazy left-event-major Cartesian product of two v7 plans. |
| `map` | `unit,operations` | Apply a validated, deterministic sequence of row transforms to each selected event, without changing its schedule. |

`operations` is an ordered array of exact `{kind,payload}` records. `kind` is a closed registry for the existing Prompt, Path, Latent, Reverse, Delete, Apply Model, Apply LoRA, Callback, prompt-trace, and source-name transforms; each payload is checked by that node's existing input/row validator. No arbitrary Python function or unserializable closure appears in a v7 plan. Row operations preserve event count and logical-row identity; only `latent_set` changes image aggregates, setting `total_images = total_batches × batch_size` and `unset_batches = 0`. `matrix_map` and `product` resolve their synthetic row first; later `map` operations apply afterward, so Prompt/Callback after Merge see the merged prompt at their own position. Adjacent maps can be combined without changing operation order.

Canonicalization is deterministic: input-order Queue concatenates child top-level units without wrapping them; alternating Queue with at least one connected input creates one `alternate`, even when that input has zero events. With no connections, either mode returns a seed `run` as specified above. `repeat(run,f)` folds into `run.count × f` for old-plan compatibility, and only **nested** repeat wrappers (`repeat(repeat(unit,a),b)`) multiply checked factors; adjacent top-level units remain separate. A factor of one may be omitted, while a zero factor retains its logical row identities but emits no events. Normal Matrix over a `run` creates one `run` per Matrix row with the original count, preserving v6 order. Empty Matrix produces no units. Merge uses the existing left-row-major run-pair order/counts unless either operand's schedule subtree contains an `alternate` unit (including under `repeat`, `map`, `matrix_map`, or `product`); in that case it uses one atomic `product`. `contains_queue_boundary` is **only** for Queue mode locking and must never trigger `product` by itself. `contains_alternate` is a derived, cacheable OR of unit kinds over the schedule subtree, recomputed and checked during normalization; it is not a second user-setting or serialized root field. `matrix_map` and `product` are never eagerly expanded into emitted batches. The root's `stats` is the checked sum of its top-level unit stats, and `change_key` hashes canonical unit kind, child order, row/operation data, effective Queue mode, boundary flag, and factors. `normalize_plan` strictly checks exact keys, cached stats, the fingerprint, finite acyclic structure, and `MAX_SCHEDULE_DEPTH=256` (root depth 0, a unit/child-plan edge adds 1); a process-local validated `ScenePlan` skips repeated validation as today. A v6 runtime plan is not accepted by a v7 evaluator; saved workflow JSON is migrated through the unchanged node definitions and defaults, not by loading an old process-local plan. A ComfyUI restart is required when installing the backend change.

For every unit, `stats` is computed without enumerating events: `run` has `(c,c×batch_size,c if latent unset else 0,1)`; `alternate` sums its inputs; `repeat` multiplies the first three statistics by its factor but retains child `row_count`; `matrix_map` multiplies all four statistics by its number of Matrix rows; `map` keeps child statistics except for `latent_set`; `product` has `batches=Lb×Rb`, `images=Lb×(Ri−Ru)+Li×Ru`, `unset=Lu×Ru`, and `rows=Lrows×Rrows`, where `L/Rb` are batch counts, `L/Ri` image totals, and `L/Ru` unset-batch counts. All four statistics and all prefix sums use checked JavaScript-safe integer arithmetic before allocation. The formula accounts for `merge_rows` preferring the right latent when set and falling back to the left otherwise.

`item_for_normalized_plan(plan, index)` remains zero-based and lazy. A plan selects a top-level unit by binary search on cached batch-prefix sums. `run` selects occurrence `index`; `repeat` selects cycle `index // child.total_batches` and local offset `index % child.total_batches`; `matrix_map` selects child index `index // M` and Matrix row `index % M`, with no lookup for `M=0`. `product` selects left index `index // Rb` and right index `index % Rb`, with no lookup for `Rb=0`. For `alternate`, input stream lengths `L_i` give `F(r)=sum(min(L_i,r))` events in the first `r` rounds: binary-search `r` with `F(r) <= index < F(r+1)`, select the `(index−F(r))`th active input in socket order, then read its local event at index `r`. `map` evaluates its operations on the selected child row. No operation expands `count` batches into Python rows. At most ten inputs are inspected per alternating level. Target memory is proportional to schedule nodes and distinct rows, not `total_batches`; lookup work is bounded by nesting depth and logarithmic count search.

Every selected event has a canonical **logical-row identity** rather than a single raw leaf. A `run` has one logical row. `alternate` offsets each input's logical-row number by prior inputs' `row_count`; top-level concatenation does likewise. `repeat` and `map` retain the child's logical-row number. `matrix_map` maps `(child_row,matrix_row)` to `child_row×M+matrix_row`. `product` maps `(left_row,right_row)` to `left_row×Rrows+right_row`. The identity includes its traversal/Queue-socket path, so two uses of one upstream source are distinct. Within a product logical row, occurrence number is `left_occurrence×right_repeat_count+right_occurrence` (zero-based); `repeat_count` is the product of the two child repeat counts. `matrix_map` keeps the child's occurrence number and count for each Matrix-derived logical row. `repeat` adds `cycle×child_repeat_count` to that logical row's occurrence. These formulas define `row_index`, `repeat_index` (one-based), and `repeat_count` without materializing all events. Plans without alternating units retain their exact v6 metadata values. Filename numbering, seed offsets, callback `exec_current_count`, and Expand's final callback use final `global_index`, never source-node evaluation order.

## Other Scene nodes

Prompt, Path, Latent, Reverse, Delete, Apply Model, Apply LoRA, Callback, and source-name tracking map selected leaf rows while preserving schedule units and their order. Callback snapshots are captured at their position in each leaf. Only nodes on the selected event path contribute to `source_node_ids`/`current_node_names`; a sibling Queue input must not leak into them. `first` remains once per callback node/run, `every` follows final event order, and Expand `last` fires after its last event.

Matrix before an alternating Queue expands each input stream in Matrix row order; the Queue then alternates their resulting batches. Matrix processes **each incoming top-level unit separately**: a plain `run` becomes Matrix-row-major runs as in v6, while an atomic `alternate`, `repeat` of an atomic unit, `matrix_map`, or `product` becomes one `matrix_map` that emits Matrix variants inline for every child event. It does not expand the whole mixed plan as a single stream and does not fuse adjacent top-level units. For example, Matrix rows `x,y` applied to `[alternate(b1,b2), run(b3,2)]` yield units `[b1x,b1y,b2x,b2y]` and `[b3x,b3x,b3y,b3y]`; Count 2 then yields the first four-event unit twice, followed by `b3x` four times and `b3y` four times. This is lazy and preserves both the old run order and alternating group boundary.

Merge without alternating units keeps the current left-row-major Cartesian order and product of row counts. When either operand contains an alternating unit, Merge defines a lazy left-event-major Cartesian product: for each event of the left stream, emit each event of the right stream, combining rows by the existing `merge_rows` rules. That product is one atomic unit for downstream Count. This is new behavior only for a composition that does not exist today. Total images must account for the merged row's right-preferred latent batch size; `left.total_images × right.total_images` is not generally correct. Empty operands yield no events. Merge/Matrix must never erase an existing alternating boundary merely to reuse the old flat implementation.

Preset expansion retains Queue mode and plan provenance. The Preset marker's Count 1 preserves units and adds its source identity without flattening. Bypass and mute use the effective plan, including through a Preset Reference. The existing model-specific LoRA selection, positive/negative resolution, seed-based `{...}` choices, and negative precedence operate on the selected event's row after index lookup.

## PNG replay and UI

Execution-path PNG replay currently rebases by `row_index` and `repeat_index` in a flat plan. For v7, the selected Expand/To Text event retains a process-local `event_ref` alongside `_plan_ref`: an ordered unit traversal path (`top-unit`, Queue socket, alternating round, Repeat cycle, Matrix row, and both left/right Product child paths), the logical-row identity, and its local occurrence. This identifies both sides of a Merge event and distinguishes two links from the same upstream node. Existing source-node ID aliases through Preset References are resolved before comparing paths. Pruning keeps the selected event and each necessary Product operand, removes other paths/sockets, and returns an explicit old-path-to-pruned-path mapping. Rank the mapped event in the pruned plan with the same index formulas, compute its new `current_index`, and derive the seed base from that rank. Recompute the Queue lock from retained effective inputs; even if pruning removes the only upstream Queue on a sibling path, the chosen event's order remains stable because the retained branch is singular. Preserve mode widget values for remaining Queue nodes and apply the same lock normalization on reopened workflow load. A missing mapped event is a hard replay error, never a silent fallback to the first event. Keep the old flat-row path for old, non-alternating plans and old PNGs. To Text and Expand each rebase against their own actual plan. Do not serialize the plan object or process-local event reference into PNG JSON.

The Queue preview shows the effective mode, lock reason, total batches/images, and only a bounded prefix of actual final-order events. `Queue A: b1,b2,...` and `Queue C: A-cycle,...,b3,...,b4,...` must agree with Expand, not merely with graph traversal order. Statistics stay scalar and must not enumerate all batches. The preview's cache/lineage key includes mode, effective upstream Queue provenance, connected source revision, and Preset revision. Browser reload, connection edit, bypass, Preset edit, and API execution converge on the same effective mode. A frontend schedule preview resolver should use the same small golden fixtures as the Python resolver; do not maintain an unrelated heuristic for alternate ordering.

## Test design and acceptance gates

| Area | Required checks |
| --- | --- |
| Backward compatibility | Existing Queue→Count, Count→Queue, Matrix→Queue, Merge→Queue, two Counts, and old `widgets_values=[]` produce identical order, prompt, seed, totals, filenames, `row_index`/`repeat_index`, and callback behavior. Missing `order_mode` in direct API input means input order; an invalid value produces a validation error. |
| Target composition | Queue A alternate + Queue B input order → Queue C input order → Count 3 emits `b1,b2,b1,b2,b1,b2,b3,b3,b3,b4,b4,b4`. Check every indexed event and final totals, not just the first and last. |
| Count placement | Unequal input lengths `b1×2,b2×3` yield `b1,b2,b1,b2,b2`; Count after A repeats this cycle. Count 2 on b1 before Queue A with b2 once yields `b1,b2,b1` (not `b1,b2,b1,b2`). Count 0 and 1, nested Counts, an empty branch, and zero-count logical rows are explicit fixtures. Two adjacent top-level repeats of `a` with factors 2 and 3 yield 5 events; nested factors 2 and 3 yield 6. |
| Round-robin | One to ten inputs, skipped empty/zero-count inputs, uneven lengths, duplicate upstream source connected twice, latent `batch_size > 1` (one batch per turn), and integer overflow. Queue with zero connected inputs in either mode yields one seed event; Count 3 after it yields three. One connected zero-event input yields no event. |
| Mode lock | Direct Queue, Reroute, Scene transform, Preset Reference, connection change, graph reload, bypass/mute, and old saved `交互` on a newly locked Queue. Test provenance through an empty Queue and Count 0. UI shows input order disabled; backend/API uses the same mode and saved widget normalizes to it. During Preset metadata loading, the choice stays unavailable, then refreshes without a full-graph rescan per draw. |
| Other operators | Prompt/Path/Latent/Reverse/Delete/Apply Model/LoRA/Callback preserve event order and selected-path provenance. Matrix mixed fixture `[alternate(b1,b2),run(b3,2)]` × `[x,y]`, then Count 2, has the exact 16-event order stated above. Merge of `alternate(a,b)` × `[x,y]` gives `ax,ay,bx,by`, repeated as one unit by Count. Merge of an input-order Queue `[run(a,2),run(b,1)]` and `[run(x,2),run(y,1)]` retains v6 order `ax,ax,ax,ax,ay,ay,bx,bx,by`. Product latent fixture: left events of batch sizes `2,3`; right events of sizes `unset,4` give four merged batches with `total_images=2+4+3+4=13` and `unset_batches=0`. Both operands empty/zero are tested. |
| Generation | Expand/To Text prompts, LoRA model selection, random choice seeds, image totals, filename counters, per-branch callbacks and final callback follow final global order. Verify first, middle, and last events. |
| Preset and PNG | Queue modes inside/outside Presets, nested Presets, saved and reloaded workflows, execution-path-only PNG replay for A/b1 and A/b2 occurrences. A selected `product(alternate(a,b),[x,y])` event `by` survives pruning with both operands and is ranked in the pruned schedule; duplicate use of `a` on separate Queue sockets remains distinct. Test changed Queue lock after sibling pruning, source aliases through Preset Reference, separate Expand/To Text rebase, and no sibling source-node IDs in `current_node_names`. |
| Frontend | Bounded Queue preview and totals match Python golden fixtures, including 160-item truncation, huge Count, mode lock/reload/disconnect, and responsive rendering. |
| Performance and validation | `10^8` repeats of a two-event alternate plan do not allocate proportional rows. Assert schedule size and lookup call counts, plus a generous memory ceiling rather than a fragile time threshold. Fuzz small schedules against a simple eager reference interpreter, comparing all indexed events, row identity, aggregates, and replay ranking. Reject missing/extra keys, inconsistent stats or fingerprint, malformed operation payloads, cycles, depth 257 (accept depth 256), and totals beyond the safe integer limit. |
| Integration | Python 3.9/3.11, frontend/browser integration, public package, real ComfyUI HTTP smoke, and end-to-end Preset/PNG replay. Do not run these against a user's active generation process. |

The design is accepted only when the same schedule fixture passes the Python resolver, browser preview, real HTTP execution, and PNG replay. No release or installed-copy update is part of this design-only change.

Implement focused resolver and serialization checks in `tests/test_plan.py` and node/operator checks in `tests/test_node_plan_semantics.py`; extend `tests/test_scene_presets.py` for saved Preset modes/provenance and `tests/test_scene_filename_prefix.py` for final-order naming. Browser lock, saved widget, capped preview, and Preset-loading fixtures belong in `tests/test_scene_browser_integration.mjs`. Reuse `tests/test_comfyui_http_runtime.py` for the eventual isolated HTTP end-to-end check. The test oracle expands only tiny fixture plans and is deliberately independent of the lazy resolver; large-count tests inspect structure and random indexed samples without materialization.
