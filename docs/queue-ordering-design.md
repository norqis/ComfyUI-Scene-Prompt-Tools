# Queue ordering and Count composition design

Status: design only; no runtime behavior is changed by this document.

## Version decision

Target package release: `v0.7.0`, provided saved workflows and documented output remain compatible. The internal `SCENE_PROMPT` plan schema changes from v6 to v7. A schema revision is not by itself a public major release. If implementation needs to change the output of an existing workflow, stop and revisit the public version and migration rather than silently shipping it. The mode defaults to the current input order. No installed ComfyUI copy should be changed while it is generating.

## User-visible contract

Scene Prompt Queue gains three independent controls: `並び順: 入力順 | 交互`, `交代する件数` (positive integer, default 1, effective only for 交互), and Queue-wide `後続Count: 乗算 | 固定` (default 乗算). Each connected socket also has an `入力の繰り返し回数` (integer >= 0, default 1). It repeats that socket's **complete incoming plan**; if the input already contains multiple batches, 3 means three copies of that complete sequence, not a promise of exactly three images. One batch is one Expand execution, not one image in a latent batch. An alternating Queue takes at most `交代する件数` batches from each socket in numbered order, skipping exhausted sockets, and continues until all connected streams are drained. A Queue with no connected inputs returns the same single seed `run` in either order mode, with Queue-boundary provenance set; it does not construct an empty `alternate`. Existing workflows and absent API values use `入力順`, block size 1, repeats 1 for every socket, and `乗算`.

`後続Count` is a property of the **whole Queue output**, not a per-socket switch. `乗算` leaves its output countable: in input order, Count repeats each top-level input unit as before; in alternate order, Count repeats the complete alternating unit. `固定` makes all units emitted by that Queue immune to later positive Count factors, even through a non-alternating Queue, Preset Reference, or a row-only transform. Count 0 always suppresses output, including fixed units. Count before this Queue has already changed its input and is never retroactively ignored. Merge creates a new combined generation unit and clears fixed protection; this explicit boundary avoids ambiguous partial protection of a Cartesian product. Matrix preserves fixed protection on the derived variants. A later Queue set to `固定` protects its entire output; one set to `乗算` retains any upstream fixed protection. No per-input mix of fixed and multiplied policy exists within one Queue.

For one-batch inputs A and B with socket repeats 3 and 2, the Queue output is `A,A,A,B,B` in input order; in alternate order it is `A,B,A,B,A` with block size 1 or `A,A,A,B,B` with block size 3. Count 10 after the Queue leaves these five batches unchanged for `固定`. For `乗算`, it emits `A×30` then `B×20` in input order; in alternate order it repeats the complete five-batch alternating sequence 10 times. This deliberately changes **order**, not each input's total count. Count 0 emits nothing in both policies. A Queue nested under another Queue keeps these same rules.

A Queue input whose effective plan already contains a Queue boundary locks the receiving Queue to `入力順`. This includes Reroutes, Scene transforms, and Preset References, not just a visually adjacent Queue. Its widget reads `入力順（上流Queueあり）` and is disabled. Connecting such an input normalizes a previously saved `交互` choice to `入力順`; disconnecting it does not resurrect that old choice. Graph load and connection changes refresh the widget. The Python node independently uses `入力順` when an input plan contains a Queue boundary, including direct API calls without the UI. A bypassed Queue leaves a boundary only if the effective bypass path actually contains one. Queue provenance is plan metadata; inspecting the whole graph at each execution or draw is unnecessary.

The backend declares `order_mode`, `alternate_block_size`, `input_repeats_json`, and `downstream_count_mode` as **optional** controls, with the defaults above, so old API prompts pass ComfyUI validation before Python defaults are used. The JSON value is a map from stable socket names (`scene_prompt1`…`scene_prompt10`) to nonnegative integer factors; omitted keys mean 1. The backend strictly validates key names/types/ranges, ignores repeat settings for disconnected sockets during execution but preserves them in the saved widget for reconnecting, and includes canonical values plus input fingerprints in `IS_CHANGED`. Invalid order/mode/block/count values are clear errors. The UI adds persistent values only after any old Queue values and presents repeat factors in one compact `入力ごとの回数` editor showing connected socket names; the serialized JSON widget is its canonical state and remains usable through API/headless workflows. The preview widget is non-serialized. Workflow/prompt serialization, connection changes, and `afterConfigureGraph` load normalization use the same effective-mode rule. A locked Queue writes `入力順` to the saved widget and submitted prompt, while Python independently enforces it for headless API callers. Preset serialization preserves every optional control. During Preset metadata loading the mode is temporarily unavailable, then refreshed from a cached Queue-boundary summary.

For the target graph:

```text
A -> b1 --\
          Queue A [交互, 交代1件] --\
A -> b2 --/                         \
                                     Queue C [入力順, locked] -> Count D [10] -> Expand
A -> b3 --\                         /
          Queue B [入力順] --------/
A -> b4 --/
```

The resulting order is `(A-b1, A-b2) × 10`, then `A-b3 × 10`, then `A-b4 × 10`. Queue A's own mode remains active. Queue C does not specify separate modes for its children. If Queue A's inputs have unequal lengths, one complete alternating cycle drains both inputs; Count after Queue A repeats that complete cycle. For example, `b1 × 2` and `b2 × 3` make a cycle `b1,b2,b1,b2,b2`, and Count 2 makes that exact five-batch cycle twice. Count before Queue A instead changes each input stream before interleaving; these two placements intentionally differ.

Count repeats each **countable top-level output unit** of its incoming plan. A run of one row is a unit; an alternating Queue is one unit. An input-order Queue with all default per-socket factors concatenates its children's top-level units and does not turn the entire concatenation into a new unit. Thus Count after an ordinary Queue remains exactly the current per-row Count for old workflows, while Count after an alternating Queue repeats the alternating sequence. A non-default socket repeat factor makes that complete socket sequence one atomic unit. Queue B's ordinary rows remain separate units when Queue C concatenates them. Positive Count factors in series multiply on countable units, Count 1 preserves structure, and fixed units remain unchanged.

## Plan representation and indexing

Plan v6 stores a flat list of `(row, contiguous count, start_index)`. Flattening an alternating Queue into that list destroys its grouping before downstream Count; materializing every batch would also use memory proportional to generation count. Plan v7 has one authoritative immutable schedule. The exact plan keys are `type`, `version`, `units`, `sources`, `contains_queue_boundary`, `stats`, and `change_key`. `sources` keeps the current Queue input summaries. `contains_queue_boundary` is a boolean set by **every** executed Queue, including an input-order Queue with zero events; transforms, Count, Matrix, Merge, and Preset markers propagate it by OR, while a bypass contributes only its effective source plan and a mute contributes none. It does not depend on leaf rows existing. Queue output sets it to true. UI lineage caches also carry this bit, so a changed empty Queue invalidates the lock state.

Each unit has a `kind` and `stats`; `stats` has exactly `total_batches`, `total_images`, `unset_batches`, and `row_count`. `unset_batches` counts events without a latent setting; their image batch size is one. Unit exact keys, in addition to `kind,stats`, are:

| Kind | Additional exact keys | Meaning |
| --- | --- | --- |
| `run` | `row,count` | One contiguous row run; zero count remains as a logical row for old metadata. |
| `sequence` | `plan` | Treat a whole ordered child plan as one atomic unit; only used when an input socket explicitly repeats a multi-unit plan. |
| `alternate` | `inputs,block_size` | One atomic chunked round-robin unit; each input is an ordered v7 plan in socket order. |
| `repeat` | `unit,factor` | Repeat the complete child unit; Count wraps each top-level unit, not every leaf. |
| `count_fixed` | `unit` | Queue-wide fixed protection on one top-level unit; positive downstream Counts leave it unchanged. |
| `matrix_map` | `unit,matrix_rows` | For each event of an atomic child, emit its Matrix variants in Matrix row order. |
| `product` | `left,right` | Lazy left-event-major Cartesian product of two v7 plans. |
| `map` | `unit,operations` | Apply a validated, deterministic sequence of row transforms to each selected event, without changing its schedule. |

`operations` is an ordered array of exact `{kind,payload}` records. `kind` is a closed registry for the existing Prompt, Path, Latent, Reverse, Delete, Apply Model, Apply LoRA, Callback, prompt-trace, and source-name transforms; each payload is checked by that node's existing input/row validator. No arbitrary Python function or unserializable closure appears in a v7 plan. Row operations preserve event count and logical-row identity; only `latent_set` changes image aggregates, setting `total_images = total_batches × batch_size` and `unset_batches = 0`. `matrix_map` and `product` resolve their synthetic row first; later `map` operations apply afterward, so Prompt/Callback after Merge see the merged prompt at their own position. Adjacent maps can be combined without changing operation order.

Canonicalization is deterministic: input-order Queue concatenates child top-level units without wrapping them after applying each connected socket's repeat factor to its **complete input plan**; a factor of 1 preserves the old unit boundaries exactly. A factor greater than 1 wraps that socket's whole plan as `repeat(sequence(plan),factor)` (or `repeat(run,factor)` for one run), preserving its internal order. Alternating Queue with at least one connected input creates one `alternate` with each repeated input plan and the chosen positive block size, even when an input has zero events. With no connections, either mode returns a seed `run` as specified above. A Queue in `固定` mode wraps each of its output top-level units in `count_fixed`; in `乗算` mode it does not add protection or remove upstream protection. `repeat(run,f)` folds into `run.count × f` for old-plan compatibility, and only **nested** repeat wrappers (`repeat(repeat(unit,a),b)`) multiply checked factors; adjacent top-level units remain separate. A factor of one may be omitted, while a zero factor retains its logical row identities but emits no events. Count factor 0 makes every unit zero-event; for positive factors it leaves `count_fixed` units unchanged and repeats every other top-level unit. Normal Matrix over a `run` creates one `run` per Matrix row with the original count, preserving v6 order; over `count_fixed`, it transforms the child and reapplies protection. Empty Matrix produces no units. Merge uses the existing left-row-major run-pair order/counts unless either operand's schedule subtree contains an `alternate` **or** `sequence` unit (including under `repeat`, `count_fixed`, `map`, `matrix_map`, or `product`); in that case it uses one atomic `product`. Merge strips `count_fixed` wrappers after computing its combinations, so its output is countable. `contains_queue_boundary` is **only** for Queue mode locking and must never trigger `product` by itself. `contains_composite` is a derived, cacheable OR of `alternate`/`sequence` unit kinds over the schedule subtree, recomputed and checked during normalization; it is not a second user-setting or serialized root field. `matrix_map` and `product` are never eagerly expanded into emitted batches. The root's `stats` is the checked sum of its top-level unit stats, and `change_key` hashes canonical unit kind, child order, row/operation data, effective Queue mode, block size, per-socket factors, count policy, boundary flag, and repeat factors. `normalize_plan` strictly checks exact keys, cached stats, the fingerprint, finite acyclic structure, and `MAX_SCHEDULE_DEPTH=256` (root depth 0, a unit/child-plan edge adds 1); a process-local validated `ScenePlan` skips repeated validation as today. A v6 runtime plan is not accepted by a v7 evaluator; saved workflow JSON is migrated through the unchanged node definitions and defaults, not by loading an old process-local plan. A ComfyUI restart is required when installing the backend change.

For every unit, `stats` is computed without enumerating events: `run` has `(c,c×batch_size,c if latent unset else 0,1)`; `sequence` copies its child plan's sums; `alternate` sums its inputs regardless of block size; `repeat` multiplies the first three statistics by its factor but retains child `row_count`; `count_fixed` copies all child statistics; `matrix_map` multiplies all four statistics by its number of Matrix rows; `map` keeps child statistics except for `latent_set`; `product` has `batches=Lb×Rb`, `images=Lb×(Ri−Ru)+Li×Ru`, `unset=Lu×Ru`, and `rows=Lrows×Rrows`, where `L/Rb` are batch counts, `L/Ri` image totals, and `L/Ru` unset-batch counts. All four statistics and all prefix sums use checked JavaScript-safe integer arithmetic before allocation. The formula accounts for `merge_rows` preferring the right latent when set and falling back to the left otherwise.

`item_for_normalized_plan(plan, index)` remains zero-based and lazy. A plan selects a top-level unit by binary search on cached batch-prefix sums. `run` selects occurrence `index`; `sequence` delegates to its child plan; `repeat` selects cycle `index // child.total_batches` and local offset `index % child.total_batches`; `count_fixed` delegates the index to its child; `matrix_map` selects child index `index // M` and Matrix row `index % M`, with no lookup for `M=0`. `product` selects left index `index // Rb` and right index `index % Rb`, with no lookup for `Rb=0`. For `alternate` with block size `k`, input stream lengths `L_i` give `F(r)=sum(min(L_i,k×r))` events in the first `r` rounds: binary-search `r` with `F(r) <= index < F(r+1)`, select the socket covering the `(index−F(r))`th event of round `r` in socket order, then read its local event at `k×r + offset_in_socket`. `map` evaluates its operations on the selected child row. No operation expands `count` batches into Python rows. At most ten inputs are inspected per alternating level. Target memory is proportional to schedule nodes and distinct rows, not `total_batches`; lookup work is bounded by nesting depth and logarithmic count search.

Every selected event has a canonical **logical-row identity** rather than a single raw leaf. A `run` has one logical row. `sequence` and `count_fixed` retain their child's logical-row number; `alternate` offsets each input's logical-row number by prior inputs' `row_count`; top-level concatenation does likewise. `repeat` and `map` retain the child's logical-row number. `matrix_map` maps `(child_row,matrix_row)` to `child_row×M+matrix_row`. `product` maps `(left_row,right_row)` to `left_row×Rrows+right_row`. The identity includes its traversal/Queue-socket path, so two uses of one upstream source are distinct. Within a product logical row, occurrence number is `left_occurrence×right_repeat_count+right_occurrence` (zero-based); `repeat_count` is the product of the two child repeat counts. `matrix_map` keeps the child's occurrence number and count for each Matrix-derived logical row. `repeat` adds `cycle×child_repeat_count` to that logical row's occurrence. These formulas define `row_index`, `repeat_index` (one-based), and `repeat_count` without materializing all events. Plans using only default Queue settings retain their exact v6 metadata values. Filename numbering, seed offsets, callback `exec_current_count`, and Expand's final callback use final `global_index`, never source-node evaluation order.

## Other Scene nodes

Prompt, Path, Latent, Reverse, Delete, Apply Model, Apply LoRA, Callback, and source-name tracking map selected leaf rows while preserving schedule units and their order. Callback snapshots are captured at their position in each leaf. Only nodes on the selected event path contribute to `source_node_ids`/`current_node_names`; a sibling Queue input must not leak into them. `first` remains once per callback node/run, `every` follows final event order, and Expand `last` fires after its last event.

Matrix before an alternating Queue expands each input stream in Matrix row order; the Queue then alternates their resulting batches. Matrix processes **each incoming top-level unit separately**: a plain `run` becomes Matrix-row-major runs as in v6, while an atomic `alternate`, `repeat` of an atomic unit, `sequence`, `matrix_map`, or `product` becomes one `matrix_map` that emits Matrix variants inline for every child event. A `count_fixed` wrapper is temporarily opened, its child mapped by that rule, and protection reapplied to every resulting unit. Matrix does not expand the whole mixed plan as a single stream and does not fuse adjacent top-level units. For example, Matrix rows `x,y` applied to `[alternate(b1,b2), run(b3,2)]` yield units `[b1x,b1y,b2x,b2y]` and `[b3x,b3x,b3y,b3y]`; Count 2 then yields the first four-event unit twice, followed by `b3x` four times and `b3y` four times. This is lazy and preserves both the old run order and alternating group boundary.

Merge without a composite unit keeps the current left-row-major Cartesian order and product of row counts. When either operand contains an `alternate` or `sequence` unit, Merge defines a lazy left-event-major Cartesian product: for each event of the left stream, emit each event of the right stream, combining rows by the existing `merge_rows` rules. That product is one atomic countable unit for downstream Count, regardless of either operand's fixed wrappers. This new order applies only to a new opt-in composition. Total images must account for the merged row's right-preferred latent batch size; `left.total_images × right.total_images` is not generally correct. Empty operands yield no events. Merge/Matrix must never erase an existing composite boundary merely to reuse the old flat implementation.

Preset expansion retains Queue mode and plan provenance. The Preset marker's Count 1 preserves units and adds its source identity without flattening. Bypass and mute use the effective plan, including through a Preset Reference. The existing model-specific LoRA selection, positive/negative resolution, seed-based `{...}` choices, and negative precedence operate on the selected event's row after index lookup.

## PNG replay and UI

Execution-path PNG replay currently rebases by `row_index` and `repeat_index` in a flat plan. For v7, the selected Expand/To Text event retains a process-local `event_ref` alongside `_plan_ref`: an ordered unit traversal path (`top-unit`, Queue socket, alternating round, Repeat cycle, Matrix row, and both left/right Product child paths), the logical-row identity, and its local occurrence. This identifies both sides of a Merge event and distinguishes two links from the same upstream node. Existing source-node ID aliases through Preset References are resolved before comparing paths. Pruning keeps the selected event and each necessary Product operand, removes other paths/sockets, and returns an explicit old-path-to-pruned-path mapping. Rank the mapped event in the pruned plan with the same index formulas, compute its new `current_index`, and derive the seed base from that rank. Recompute the Queue lock from retained effective inputs; even if pruning removes the only upstream Queue on a sibling path, the chosen event's order remains stable because the retained branch is singular. Preserve mode widget values for remaining Queue nodes and apply the same lock normalization on reopened workflow load. A missing mapped event is a hard replay error, never a silent fallback to the first event. Keep the old flat-row path for old, non-alternating plans and old PNGs. To Text and Expand each rebase against their own actual plan. Do not serialize the plan object or process-local event reference into PNG JSON.

The Queue preview shows effective order mode, block size, per-socket repeats, fixed/multiplied Count policy, lock reason, total batches/images, and only a bounded prefix of actual final-order events. `Queue A: b1,b2,...` and `Queue C: A-cycle,...,b3,...,b4,...` must agree with Expand, not merely with graph traversal order. Statistics stay scalar and must not enumerate all batches. The preview's cache/lineage key includes all four Queue controls, effective upstream Queue provenance, connected source revision, and Preset revision. Browser reload, connection edit, bypass, Preset edit, and API execution converge on the same effective mode. A frontend schedule preview resolver should use the same small golden fixtures as the Python resolver; do not maintain an unrelated heuristic for alternate ordering.
